# Fork changes

This fork of [herdrdev/herdr-core](https://github.com/herdrdev/herdr-core) is the hc build used day to day with the herdr-app fork. It tracks upstream by merging upstream releases or `upstream/master` into `master`. This file is the inventory of what diverges from upstream.

## Changes

### Build identifier

`feat/build-tag` (fork only): a fork build says which commit it is, beside an unchanged version. `crates/herdr-core/build.rs` runs git (`crates/herdr-core/fork_build.rs`) and sets `HERDR_FORK_BUILD` to `fork.<short sha>`, with `.dirty` when tracked files differ from HEAD; without git (a tarball) it is unset. No `Cargo.toml` edit, so upstream syncs stay clean.

- Shown: `hc --version` prints `hc 0.1.20 (fork 8cc5ec1)`; `hc server status` (`server.status`) carries `"build": "fork.8cc5ec1"` next to `"version": "0.1.20"`, or `"build": null` without git. `schema/hc.openrpc.json` gains the field; `schema/released.openrpc.json` is upstream's and stays as it is.
- The version stays upstream's everywhere it is compared or sent: `hello` (apps' compatibility check, remote machines and mirrors), `server.status`'s `version`, the OpenRPC document, `hc update` (`older`, release manifests and downloads), machine installs and `distribution/macos-Info.plist`. Readers of a `--version` line cut a fork build's ` (fork …)`: `cli/update.rs`'s `version_of` (`hc update --from`) and `scripts/mac-bundle` (the bundle's `Info.plist`). `distribution/install.sh` compares only the numbers, and `install.ps1` only prints the line. `hc machine add` and `hc machine update` print the remote hc's whole `--version` line, fork part included: display only, nothing compares it.
- Rebuilds: build.rs reruns when HEAD, its reflog, its branch or `packed-refs` change (paths from `git rev-parse`, so worktrees work), and on edits under `crates/herdr-core/src`. Not on index changes: editors and `git status` rewrite the index, and each rerun recompiles the crate. So an edit elsewhere in the workspace, or a staged-only change, does not mark the build `.dirty` until something else reruns it. Worktrees need their own target dir (the default): Cargo hashes a package by its path within the workspace, so a shared `CARGO_TARGET_DIR` could keep another worktree's build.
- Tests: `fork_build::tests` (the `--version` line, a well-formed build, git in a temporary repository: no git gives none, a commit gives its sha, an edit adds `.dirty`, untracked files do not), `tests/m0.rs` (`server status` keeps the version and has a `build`).
- Files: `crates/herdr-core/{build.rs, fork_build.rs, src/fork_build.rs, src/lib.rs, src/api.rs, src/api/types.rs, src/cli.rs, src/cli/update.rs, tests/m0.rs}`, `schema/hc.openrpc.json`, `scripts/mac-bundle`

### A piped observer ends at end of input

`fix/observe-eof` (fork fix, upstream PR #184): `hc attach --observe` with a stdin that is not a terminal and reaches end of input (`< /dev/null`, a closed pipe) spun at about 100% CPU. At EOF stdin stays readable, so `read_stdin` returned None at once on every turn and the attach loop's `None => {}` waited on it again. The loop now ends on None whether or not stdin is a terminal, as the `detached = !tty` comment intended, and prints `[detached from <address>]` like a closed window. (A piped attach without `--observe` is refused before the loop, `attach.rs` `run`.) One loop serves Unix and Windows, whose `read_stdin` also returns None at end of input, so both are fixed.

- Tests: `tests/m2.rs` `a_piped_observer_ends_when_its_input_does` (exits within 5 s, success, the terminal stays live).
- Files: `crates/herdr-core/src/attach.rs`, `crates/herdr-core/tests/m2.rs`

### A launch task ends when its agent exits to the shell

Upstream (`72ab4ae`, #166, in 0.1.20) resets a terminal's status when its root interactive shell is back in front (`watch_foreground` in `crates/herdr-core/src/foreground.rs`): an agent typed at a prompt, or started by Herdr's `"$@"; exec "$0" -li` wrapper, no longer leaves its last word (often `blocked`) on the terminal after a crash or Ctrl-C. That reset also drops a pending launch task (`first_task_turn`) but tells nobody, so a parent's `hc wait --children --any` kept waiting when the agent given that task exited without ending a turn.

Fork fixes on upstream's reset, all upstream candidates:

- News (`c01e095`): as when the program exits, a launch task let go without an ended turn is news, so the parent's wait returns.
- No status left: upstream resets only while a status or record remains, so an agent that cleared its status (`state=clear`) before exiting kept its launch task pending for good. The reset also runs when a launch task is pending on a terminal that has reported. A program that never reports, a plain shell given a task, keeps its task until it ends, as upstream does: the shell is in front between its commands, and would let the task go at once.
- Crash replay: adopting a holder after a crash replays its tail's OSC 7501 reports, which still hold an ended job's last word. With the shell in front, the next poll reset it again and counted a second turn for one job, with `status` and `turn` events in between. When the saved record has its root shell in front (`foreground::at_root_shell`, the same test as the reset), the saved foreground can be stale: a job may have started and reported after the last save (a sub-record or a repeated word waits up to 2 s for it, and the core may stay down longer). So adopt keeps that tail in memory (`State.crash_tails`, not saved) and the first foreground poll that gets an answer from the holder decides: the shell still in front drops it (its job ended and was reset); a job in front replays it as any crash tail (`Core::replay_crash_tail`, the same turn and event rules). A holder that can't say (no link yet, a busy holder past the 1 s query timeout right after an adopt, a relink in progress, or `about` failing) leaves the tail for the next poll; after 3 s without an answer (`CRASH_TAIL_WAIT`) it is replayed anyway. A newer report drops a waiting tail, and so does the terminal's end. Until that poll (`HC_FOREGROUND_MS`, 500 ms by default) the record shows what was saved. A dropped tail's side facts (`reported`, sub-records) go too: `reported` is already saved from before the crash, and the reset clears sub-records anyway.
- Crash-replay limits, accepted: if a different job is in front at that first poll (`less`, `make`, or an agent that hasn't reported yet), the ended job's tail is replayed onto it, so it can show the old job's last word and count a turn when it exits. A job that starts, reports and ends entirely while the core is down is not counted.
- Behaviour change accepted with upstream's rule (the fork's own reporter tracking is dropped, see the 0.1.20 sync): an agent inside a nested shell in a tab (`bash`, `nix develop`, `poetry shell`) keeps its last status after it exits, until that shell exits; a job stopped with Ctrl-Z at a plain prompt has its status cleared, as does a status the shell itself reported.
- Tests: `tests/m7.rs` `a_launch_task_ends_when_the_agent_given_it_exits_to_its_shell` (Herdr's wrapper shape: the agent, then `exec sh -i`; with its status left, and cleared before it exits, which fails without the no-status fix); `tests/m5.rs` `a_job_that_exits_to_its_shell_takes_its_status_with_it` (the `status` and `turn` events of the reset), `a_jobs_status_survives_a_core_restart_or_crash_and_still_ends_with_it` (a restart or crash keeps a running job's status, and after its reset a restart or crash leaves it reset), `a_crash_replay_does_not_bring_back_a_job_that_ended_at_its_shell` (it waits for the reset on disk, then: no status right after adoption and no second turn; without the crash-replay fix it reads `working` after adoption), `a_job_started_after_the_shell_was_saved_adopts_with_its_status` (polls 5 s apart: a job reports a sub-record that isn't saved yet, the core dies, and the new core's first poll brings it back; dropping waiting tails fails it). On Linux both check the new core's `HC_FOREGROUND_MS` in `/proc/<pid>/environ`. A macOS core started through launchd gets its environment over a socket, which `ps` doesn't show, so there the 5 s test's timing is the check: no replay 1.5 s after adoption, then the replay. A possible CI flake in that test: it relies on the old core's next poll being 2–3 s away when `crash()` runs (the shell was saved about 2 s after a poll). A loaded runner that delays the job's report by that much lets a poll see the job and save it, and the "saved with the shell in front" assertion fails. The holder-can't-say wait has no test: making the foreground query fail on cue needs a fault hook in the holder.
- Files: `crates/herdr-core/src/{foreground.rs, runtime.rs, viewers.rs}`, `crates/herdr-core/tests/{m5.rs, m7.rs}`

### An adoption announces the status it changed

`15f9f14` (fork fix, upstreamed as herdrdev/herdr-core #183, `63de05a`, in 0.1.21; the code and tests are upstream's). The fork's only addition is that the deferred crash-tail replay above goes through the same `Core::replay_crash_tail`, so it announces too. Adopting a holder without a handover (a core start after a crash, or the relink after reading a holder fails) replayed the tail's OSC 7501 reports into the record but never told subscribers, so `hc get` said one word while event streams kept the old one until they resubscribed. The relink case happens inside a live core with subscribers attached. The core compares the status facts before and after the replay and emits one `status` event with the final facts when they differ, none when the tail only repeats what subscribers already heard. Turn counting and `status_ms` are unchanged.

- Tests: `runtime::tests::adopting_a_holder_announces_a_status_its_tail_changed`, `adopting_a_holder_whose_tail_repeats_the_status_announces_nothing`.
- Files: `crates/herdr-core/src/runtime.rs`, `crates/herdr-core/src/runtime/tests.rs`

### The holder gathers a burst of small reads into one frame

`perf/pump-coalesce` (fork change, upstream candidate for herdrdev/herdr-core #201): holder CPU followed the program's write count, not bytes. `yes` writes 2 bytes at a time, and the holder paid a poll, a read of a few bytes, a hand-off to its writer thread and a `sendto` for each, about 2.3 µs; the core and every viewer then paid a frame each. `Gather::read` (`crates/herdr-core/src/holder.rs`): a read under 512 bytes (`SMALL_READ`) that comes within 1 ms (`BURST_GAP`) of the last such read sleeps (`GATHER_WAIT`, 200 µs), then takes what arrived without waiting (`PtyOutput::read_now`) up to the 64 KiB frame (`FRAME_BYTES`), as one frame. The first read after a quiet spell or after a big read (a keystroke echo, the prompt after a `cat`) goes at once. The wait halves, down to 16 µs (`GATHER_WAIT_MIN`), while 512 bytes or more arrive during it, since a writer that fast would fill macOS's 1 KiB PTY queue and stall, and doubles back otherwise. An end or error found while gathering is left for the next read, after the gathered bytes went out. Unix only (`GATHERS`): Windows' ConPTY batches its output already, and the wait there is unmeasured. Measured on macOS only.

- Cost: a write within 1 ms of a small one waits one sleep (macOS: 200 µs asked, about 270 µs taken; see the PR for latency percentiles).
- Tests: `holder::tests` (a lone write and a small write after a big read take nothing after them; a burst arrives in far fewer frames with the same bytes in order; the cap; the wait shrinking and growing back; an end or error after gathered bytes), `tests/m1.rs` `a_burst_of_tiny_writes_arrives_gathered_and_whole` (20000 five-byte writes: every byte in order before the exit, under a tenth as many frames), `releasing_a_terminal_mid_burst_stops_it_cleanly`.
- Files: `crates/herdr-core/src/{holder.rs, platform/mod.rs, platform/unix.rs, platform/windows.rs}`, `crates/herdr-core/tests/m1.rs`

### An autostarted core takes the service manager's environment

`fix/autostart-service-env` (fork PR #7, fork only: upstream declined it as herdrdev/herdr-core #231, since tools only on the caller's PATH stop being found after an implicit start): a core that starts on its own (any `hc` command, `hc connect` from the app, a plugin, a holder restarting a crashed core) takes the service manager's environment plus hc's own settings (`platform::starter_setting`), not the starting client's. launchd's on macOS (`macos_launchd.rs` `Inherited::settings`), the systemd user manager's on Linux (`systemd.rs` `starter_env`), a new login's on Windows (`windows_env.rs` `service_base`). `hc server start` and `hc server restart --fresh` hand over the caller's environment; planned restarts keep the retiring core's. Without a service manager the core still takes the caller's.

- Upstream's own fix for remote Linux cores (`df5474b`, `platform/linux_login.rs`) sits on top: a new core started over ssh on Linux captures the login shell's environment and sets it on the start command. That capture starts from the caller's environment, so most of it repeats the caller's. On the systemd path `systemd::spawn` keeps, for a core, only the command's variables that hc's settings and session rule allow or whose value the login's profile changed from the caller's (`command_var_reaches_core`): those reach the core, the caller's unchanged variables stay with the caller, and the rest comes from the user manager. Limits, accepted to keep upstream's capture as it is: a changed value carries what the caller already had in it (a profile that prepends to PATH passes on the caller's PATH after its own entries), and a caller that is itself an interactive login shell, having run the same profile, passes on nothing from it. Without a user manager the core takes the captured environment whole, as upstream's does. Local starts are unchanged.
- Upstream's recursion guard (`3453f99`, 0.1.21): the capture runs the login shell with `HC_LOGIN_CAPTURE` set, and an `hc` that a login profile runs during the capture skips its own capture. If that inner `hc` autostarts the core, on the systemd path the core gets the user manager's environment and hc's settings but nothing the profile changed (no capture happened, and the inner `hc`'s other variables count as the caller's under the fork's rule, so they stay out); it usually wins the start lock, so the first ssh-started core misses that profile's changes. Accepted, like the interactive-login limit: upstream's own path would hand over the inner `hc`'s environment, the profile only partly run. Without a user manager the inner core takes that partial environment, as upstream's does. The fork's explicit start and `restart --fresh` drop `HC_LOGIN_CAPTURE` from the environment they hand over (`cli/server.rs` `handed_over`), since `starter_setting` would otherwise keep it as an `HC_*` setting across restarts.
- Tests: `tests/environment.rs` (`a_core_a_command_starts_takes_launchds_environment_not_the_callers`, `a_core_the_app_connection_starts_takes_launchds_environment_not_the_callers`, `an_explicit_start_takes_the_callers_environment_and_restarts_keep_it`, `starting_a_running_core_leaves_its_environment_alone`), `macos_launchd::tests`, `systemd::tests::{a_core_takes_the_managers_environment_but_a_holder_takes_its_cores, a_core_takes_only_what_an_ssh_logins_profile_changed}`, `cli::tests::a_start_hands_over_the_shell_without_the_login_capture_mark`.
- Files: `crates/herdr-core/src/{cli.rs, cli/server.rs, cli/tests.rs, platform/mod.rs, platform/macos_launchd.rs, platform/systemd.rs, platform/windows.rs, platform/windows_env.rs}`, `crates/herdr-core/tests/environment.rs`, `README.md`, `crates/herdr-core/src/SKILL.md`, `docs/commands.md`

### The title stack

`fix/title-stack` (fork fix, upstream candidate): a program that saves the title, sets its own and restores it on exit left its own title behind. libghostty-vt parses XTWINOPS 22 and 23 but keeps no stack (`stream_terminal.zig`: "no terminal-modifying effect"), and Ghostty's own app layer (`termio/stream_handler.zig`) ignores them too. So the terminal's `title`, its `title` event and a viewer's screen all kept the program's title.

- Who sends it: Neovim 0.12 under `xterm-256color` (the `TERM` the core sets) sends `CSI ?1049h CSI 22;0;0t` as it enters the alternate screen and, with `title` set, `CSI 22;0t` and `OSC 0;<file> - Nvim`; at exit `CSI 23;0t`, then `CSI ?1049l CSI 23;0;0t` (with `titleold` set, an `OSC 0;<titleold>` before the first restore). Claude Code's prompt editor runs it so. Recent ncurses' `xterm-256color`, as Linux distributions ship it, puts the same 22/23 pair into smcup and rmcup (not checked on a Linux machine here), so there every full-screen program (`less`, `htop`, `man`) saves and restores the title too, and each such exit now sends a `title` event even when the title doesn't change, as any OSC title does. macOS's own terminfo has a plain smcup.
- The stack: `ghostty_vt::Terminal` keeps it beside the screen (`push_title`, `pop_title`), following xterm. `which` 0 or 2 saves and restores the window title; 1 saves only the icon title, which takes a slot but restores no window title (a terminal here has no icon title); other values take an empty slot, as in xterm. A missing parameter is 0. Index 0 pushes or pops; index n replaces or reads the nth entry from the bottom without popping. It holds 10 entries, and a push past them drops the oldest. A pop on an empty stack does nothing. A program killed inside a full-screen program leaves its entry, which the next unmatched restore takes, as in xterm.
- Differences from xterm, only reachable by misusing the stack: a window restore from an icon-only entry restores nothing (xterm looks further down for a window title), an index past the entries does nothing, and after a push past 10 entries an index counts from the oldest kept one (xterm counts ring slots). A title never set saves as empty, where xterm saves its window name.
- No vendor patch: the relay (`relay.rs`), which already holds each escape sequence until it can judge it, recognises `CSI 22/23 ; which ; index t` (`title_stack`) once the screen has taken it. The app's own screen keeps no stack either, so the title has to travel in the output regardless.
- A restore reaches every client as an OSC title change does: after the program's `CSI 23 t` the relay passes `OSC 2;<title> ST` to the screen and to viewers. The screen's title hook then sets the terminal's `title` and emits its `title` event (`viewers.rs` `output`), and a viewer's own screen (the app's tab, `hc attach` in another terminal) takes the title whether or not it keeps a stack. A viewer with a stack of its own, attached before the save, restores the same title first; one attached later restores whatever it had, and the OSC 2 then corrects it. Viewers still get the program's 22 and 23 unchanged.
- Restarts: a planned restart (handover) saves each stack in the registry (`Registry.titles`) beside the screen snapshot it belongs to, and the new core sets it on that screen before replaying the tail; a terminal whose holder hasn't come back since an earlier handover keeps its saved stack. A title with a control character in a saved stack restores nothing, since none can come from an OSC. A terminal whose screen wasn't saved gets none. A crash or a relink rebuilds the screen from the holder's tail, and the stack from what that tail pushes: a push older than the tail is lost, so its restore does nothing and the title stays as the program left it.
- Not seen by the relay: a `CSI 22/23 t` with a control character inside it, or right after an OSC that ESC cut short (the relay holds that OSC whole); one inside the bytes `feed_to_ground` hands the screen directly, which finish an oversized string a recovering viewer missed; and one a handover cut in half (its start goes to the screen with the snapshot, and the new core's relay sees only the rest). The screen acts on each, so only the restore is missed.
- Also kept as before: a viewer that fell behind is repainted with a title only when the title isn't empty (`paint`), so an empty title restored during that backlog leaves its screen's old one. The terminal's `title` and event are right.
- Upstream's three questions: does the app act on it? No: the core keeps terminal state, and the app shows the title the core reports and the one its own screen parses. Can only the app see it? No: the core sees the program's output. Can a mod not do it? Yes: no mod can know the title a program saved. Verdict A (as is).
- Tests: `ghostty_vt` `the_title_stack_pops_in_order_and_an_empty_pop_restores_nothing`, `an_icon_title_entry_takes_a_slot_but_restores_no_window_title`, `the_title_stack_keeps_the_newest_ten`, `an_index_reads_or_replaces_a_saved_title_in_place`, `a_restored_title_stack_keeps_the_newest_ten_and_no_control_characters`; `relay::tests::a_restored_title_reaches_the_screen_and_viewers_as_an_osc_title` (Neovim's whole trace, at once and byte by byte, and restoring an empty title), `a_restore_with_nothing_saved_or_no_window_title_changes_nothing`, `title_stack_sequences_follow_xterms_parameters`; `runtime::tests::a_restored_title_is_announced_like_any_title_change`; `tests/m1.rs` `a_title_a_program_saved_comes_back_when_it_restores_it_even_after_a_restart` (fails if the new core doesn't set the saved stack).
- Files: `crates/ghostty-vt/src/{lib.rs, tests.rs}`, `crates/herdr-core/src/{relay.rs, runtime.rs, runtime/tests.rs, terminals.rs}`, `crates/herdr-core/tests/m1.rs`

## Not carried

### Blocking PTY reads with a signal wake (upstream #202)

The fork runs upstream's `PtyIo` (`de6cc39`, 0.1.19): the holder's master is non-blocking, and each read and write polls the master and the `Pty`'s stop socket first. Apart from the gathered reads above (`Gather`, `PtyOutput::read_now`, `to_core` taking the frame by value), `crates/herdr-core/src/platform/unix.rs` and `crates/herdr-core/src/holder.rs` are upstream's; at each sync, `git diff upstream/master -- crates/herdr-core/src/platform/unix.rs crates/herdr-core/src/holder.rs` shows only those.

- What #202 was: `up/ptyio-blocking-wake` (`12a1cb1` to `2fe4214`) made the master blocking again, so a read was one syscall per chunk, and ended a release's IO with `SIGURG` sent to each thread inside a read or write. The fork merged it (`edc6263`) with a follow-up (`ba309fa`, `76dc61b`: each IO thread unblocks `SIGURG` before its first call). Both are reverted (`2d270ab`, `c7e4153`).
- Why not: upstream declined #202 (closed 2026-11-11): on its Linux runs the CPU difference was within noise, about 1% either way on most workloads, not worth trading the simple poll-based stop for a signal-based one. Its review also found a leak the fork's follow-up fixed: with `SIGURG` blocked in the IO threads, a release timed out and the program could still read input. On macOS, 7 interleaved passes per side, each with a fresh isolated core, over the five workloads of upstream #201, poll against blocking: holder syscalls +16–20% (+49% for a no-viewer 15 MB `cat`), instructions +12–14% (+30%), holder CPU +4–6% (+20% for the `cat`: 197 ms against 163 ms). Poll's CPU was higher in 32 of 35 pass pairs, and its syscalls and instructions in all 35, so the cost is consistent but small; each workload's CPU min–max ranges overlap. The machine ran at a 1-minute load of about 7 with other builds and benchmarks alongside, which widens every range. Carrying a signal-based wake, its thread bookkeeping and the signal-mask rule for that is not worth diverging from upstream on the holder's IO path.
- Correctness: going back to poll gives up no behaviour. A release still ends the reader and writer of a terminal a detached program holds, through the stop socket (upstream's `tests/ghosts.rs` `closing_detached_terminals_releases_the_holders_pty_masters`, Linux only), and poll never opens the slave, so a terminal its program made exclusive (`TIOCEXCL`) is no special case. The stray-`SIGURG` `EINTR` rule and the drop outside the holder lock go with #202.
